## 1. Executive Summary

Between v0.3.4 and v0.8.14 the app moved from an early prototype to a substantially more complete application. The headline changes:

- **App-wide access control was re-architected.** `App.OnStart` grew from a 1-line version stub into a full role-based access-control, user auto-provisioning, and impersonation engine. The dynamic navigation menu moved out of `Dashboard.OnVisible` and into `App.OnStart`.
- **A new class/session picker flow** (`ctn_PopUp_ClassPicker`) was added to the **POCSUPERVISOR** screen — this is the single largest change (`+75 KB`). It captures training scenario, role, date/time session, and location into a set of `varPopUp_ClassPicker_*` variables.
- **A brand-new screen `alt_ManageDesks`** (`~510 KB`) was added — a modern responsive-layout CRUD form for adding/editing/deleting `Desks` SharePoint records.
- **The Dashboard was redesigned** (dark-blue theme, role-aware welcome/access-denied messaging, author/version timer).
- **The three calendar screens** (`scrn_MoCalendar`, `scrn_WeeklyCal`, `scrn_DailyCal`) received layout/visibility refinements.
- **`chkWeekDays` was reorganized** — many loose top-level controls were consolidated under group containers.
- **Assets grew from 6 → 38 images**; a new **`Tabs_altColor`** component was added.
- **Data sources and connections were unchanged** (no SharePoint schema or connector changes at the app-manifest level).

## 1A. Functional Impact & Design Rationale — the "Why" Behind the Changes

This section explains *what each change accomplishes for the end user* and *why it was made*, rather than merely which lines moved. It is organized around the four big themes that drove the v0.3.4 → v0.8.14 evolution.

### Theme 1 — Role-Based Access Control (RBAC): the single most far-reaching change

**What it is.** Every user is now classified into exactly one of eight access levels, read live from the `DeskAccessControl` SharePoint list on a **per-user, per-session basis** (resolved in `App.OnStart`, cached in `userAccessLevel_text`, with the boolean shortcut `user_isAdmin = (level = "AppAdmin")`):

`AccessDenied` → `View-only` → `User` → `SuperUser` → `Manager` → `ServiceChief` → `ProjectLeader` → `AppAdmin`

**Why it was added.** In v0.3.4 the app had essentially no gating — anyone who opened it saw the same menu and could interact with everything. The new model lets the EHRM Training Coordinators grant, restrict, or revoke access centrally (by editing one SharePoint row) **without republishing the app**, and lets the app present a tailored, least-privilege experience to each person.

**What actually becomes visible / invisible / enabled / disabled as a result.** The access level is not cosmetic — it is wired into concrete controls throughout the app:

| Surface / Control | How the access level changes it |
|---|---|
| **Navigation menu** (`colMenu`, rendered by the `Tabs` component on Dashboard, MyAppts, ManageDesks, Reservation, Success) | The menu is *rebuilt per role*. **Elevated** roles (SuperUser/Manager/ServiceChief/ProjectLeader/AppAdmin) get **Home · My Bookings · Create New · Manage Rooms**. A plain **User** gets **Home · My Bookings · Create New** (no *Manage Rooms*). **View-only** gets **Home · My Bookings** only (no *Create New*, so they cannot start a booking). **AccessDenied** gets an **empty menu** — effectively no navigation at all. |
| **Dashboard welcome panel** (`HtmlText2`, `lblNoResDashboard`) | **AccessDenied** users see a bold **"ACCESS DENIED!"** headline plus an HTML notice with a pre-addressed mailto link to the coordinators. **View-only** users see a "VIEW ONLY" explanation. Everyone else sees the normal welcome + Learning Lab resource links. The greeting is personalized (`"Welcome, <GivenName>!"`) from the resolved access record. |
| **Calendar screens** (`scrn_MoCalendar`, `scrn_WeeklyCal`, `scrn_DailyCal` galleries) | The event galleries' `DisplayMode` is driven by level: **User and above → `Edit`** (can click days/slots to act), **View-only → `View`** (read-only browsing), **AccessDenied/blank → `Disabled`** (greyed out, no interaction). The calendar **`Items` filter also differs**: a plain **User** sees only reservations where they are the `Created By`/`Reserved By`; **elevated roles** see the full/shared calendar; **View-only** sees their own; **AccessDenied** sees nothing. |
| **Admin-only controls** (`user_isAdmin`) | Several controls appear **only for `AppAdmin`**: the `RESET` button (`Button1`) on POCSUPERVISOR; the `shape_hiddenUnlessAdmin` overlay and associated recurrence/booked-slot controls on `chkWeekDays`; and the impersonation controls on the Dashboard (see Theme 2). |
| **"My" data everywhere** (`MyAppts`, Dashboard preview gallery) | All "my reservations" queries were re-pointed from `User().Email` to `Lower(varDeskAccessControl_record.Email_Text)`, made **case-insensitive**, and thereby made **impersonation-aware** (see Theme 2). |

**Net effect:** the same published app now renders as four materially different experiences (denied / view-only / standard / elevated), all controlled from SharePoint data.

### Theme 2 — Impersonation ("act as another user"): an admin support/testing tool

**What it is.** On the Dashboard, admins (and the developer account `Kyle.Coder@va.gov`) see a hidden `modernCombobox` (`Combobox1`) + status button (`Button6`) that let them pick **any** user from `colDeskAccess` and have the entire app **re-render as that person**. Selecting a target re-resolves `varTargetEmail`, `varDeskAccessControl_record`, `userAccessLevel_text`, `user_isAdmin`, `varUser_details` (their O365 profile), and rebuilds `colMenu`.

**Why it was added.**
- **Support/troubleshooting:** an admin can reproduce exactly what a specific user sees ("why can't I book?") without that user present.
- **Booking on behalf of others:** the POCSUPERVISOR class-picker prompts are personalized to the *target* user (e.g. *"Pick a SCENARIO for **Jane's** Learning Lab"*), so a coordinator can register someone else for training.
- **Safe by design:** the real signed-in identity (`varRealEmail`/`varRealEntraID`) is captured separately and can never be spoofed; the auto-provisioning `Patch` is guarded to **only ever write for the real user, never while impersonating**, so acting-as cannot accidentally create/modify other people's access rows.

### Theme 3 — Zero-touch user onboarding (auto-provisioning)

**What it is.** In `App.OnStart`, if the signed-in user has no `DeskAccessControl` row, the app automatically `Patch`es one in with a default `"User"` level, timestamps, their Entra ID, and their manager's email (looked up via `Office365Users.Manager`), then re-reads it.

**Why it was added.** Previously (v0.3.4) there was no self-service path — access had to be arranged manually. Now **any authenticated Hines user gets baseline access on first launch** and immediately appears in the `DeskAccessControl` list, where a coordinator can later elevate or restrict them. It also guarantees downstream formulas always have a non-blank access record to read (falling back to `AccessDenied` only if truly unresolved).

### Theme 4 — Training-aware bookings (the Class/Session Picker)

**What it is.** The POCSUPERVISOR "Create New" flow gained the `ctn_PopUp_ClassPicker` popup, which appears after the user clicks CONTINUE and walks them through four cascading choices — **Scenario → Role → Date/Time session → Location** — captured into `varPopUp_ClassPicker_*` variables (including regex-parsed start/end times, 24-hour markers, and day-of-week).

**Why it was added.** In v0.3.4 a reservation was just a desk/room + time; it wasn't tied to *which* EHRM training event it was for. The picker makes each booking **describe the specific Learning Lab / VILT session** being attended. Concrete benefits:
- **Direct link to course materials:** the Scenario selection builds a deep-link into the SharePoint Learning Lab **Workbook** library filtered to that scenario, so attendees can open the right materials in one click.
- **Personalized, reviewable prompts:** each step names the (possibly impersonated) attendee, and the selections are echoed back on the **Confirm** screen for a final check before submit.
- **Foundation for reporting:** scenario/role/session/location become structured data that can (once persisted — see §9) drive attendance reports and Power BI dashboards.

### Theme 5 — Supporting redesigns that serve the above

- **Dashboard redesign** (dark-navy theme, mascot banner, role-aware messaging, author/version timer) gives the app a finished, branded landing page and is the *host* for the RBAC messaging and impersonation controls.
- **`alt_ManageDesks`** is a modern, responsive **CRUD console for the `Desks` list** (add/edit/delete via `NewForm`/`Patch`/`Remove`). It is staged alongside the legacy `ManageDesks` so admins can manage the room/desk inventory that feeds `DeskSelect` and the reservation flow, ahead of a planned cutover.
- **Calendar layout/visibility work** improves at-a-glance readability of who has what booked, and (as noted in Theme 1) enforces the view/edit distinction per role.

## 3. App-Level Changes

### 3.1 `App.OnStart` — complete rewrite

**v0.3.4 (old):** a single `Set(varGetRepo_ProjectVersion, "0.3.4")` with commented-out GitHub/PowerApps-for-Makers experiments. `StartScreen` was blank.

**v0.8.14 (new):** a full startup routine, organized into 6 commented sections:

1. **Initialization & setup** — sets `varTimer`; captures the real signed-in identity (`varRealEmail`, `varRealEntraID`); establishes an **impersonation model** (`varTargetEmail`, `varTargetEntraID`, `varIsImpersonating`); refreshes `DeskAccessControl` and `ClearCollect`s `colDeskAccess`, `colUser_details` (via `Office365Users.UserProfileV2`), `colMenu`, `CollectionRecurrence`; sets `varRepoVersion` and `user_isAdmin`.
2. **Find target user's existing record** — `LookUp(colDeskAccess, ...)` into `varDeskAccessControl_record`; sets `varUserExists`.
3. **Auto-provision missing users** — if the (real) user has no record, `Patch`es a default `"User"` access record into `DeskAccessControl` (with manager lookup via `Office365Users.Manager`), then re-reads it. Guarded so it never writes while impersonating.
4. **Resolve access level** — `userAccessLevel_text` via `Coalesce(...AccessLevel_Text, "AccessDenied")`.
5. **Elevated/admin flag** — `user_isAdmin = (userAccessLevel_text = "AppAdmin")`.
6. **Build role-based navigation menu** — `Switch` over access level populates `colMenu` for elevated roles (Home / My Bookings / Create New / Manage Rooms), standard users (no Manage Rooms), view-only (Home / My Bookings), and empty for AccessDenied.

Also: **`StartScreen` changed from blank → `Dashboard`**.

> **Architectural note:** menu construction previously lived in `Dashboard.OnVisible` and was **moved to `App.OnStart`**, so the menu is now built once at launch rather than on every Dashboard visit. Menu labels were also renamed (e.g., `"Dashboard"` → `"Home"`, `"Book"` → `"Create New"`, `"Manage Rooms"` retained).

### 4.2 POCSUPERVISOR (`POCSUPERVISOR.fx.yaml`) — largest change

The core "create a booking" screen. Retains `Label16`, `Form1`, `btnContinueDate_1`, `btnBackDate_1`, `lblSelectDate_1`, `grpHeader_11`, and **adds** two new top-level elements:

- **`ctn_PopUp_ClassPicker`** (`groupContainer.manualLayoutContainer`) — a modal-style popup shown when `varPopUp_ClassPicker = 1`. It contains nested sub-containers:
  - `ctn_PopUp_ClassPicker_Header` — title/instructions + a live HTML summary of the current selections.
  - `ctn_PopUp_ClassPicker_Scenario` — training scenario dropdown (`Dropdown3`); also builds a deep-link to the matching Learning Lab **Workbook** materials on SharePoint (`varPopUp_ClassPicker_scenarioSplit` = space-encoded scenario name).
  - `ctn_PopUp_ClassPicker_Role` — role dropdown (`Dropdown3_1`).
  - `ctn_PopUp_ClassPicker_DateTime` — session date/time dropdown (`Dropdown3_2`). Uses `Match`/`MatchAll` regex to parse the selected string into date, start time, end time, 24-hour markers, and day-of-week.
  - `ctn_PopUp_ClassPicker_Location` — location dropdown (`Dropdown3_3`).
- **`Button1`** (`modernButton`) — a `RESET` button that clears all four class-picker dropdowns. *Functional impact:* **visible only to `AppAdmin`** (`Visible: =user_isAdmin`), i.e. an admin convenience for quickly re-testing the flow, hidden from normal users.

**`OnVisible`** (was empty in v0.3.4) now manages picker state: when `varPopUp_ClassPicker = 0` it `Concurrent`-clears all `varPopUp_ClassPicker_*` variables and resets `Dropdown3`/`3_1`/`3_2`/`3_3`; when `= 1` it re-hydrates those variables from the dropdowns' current selections (including the regex date/time parsing).

**Variables introduced** (captured for later confirmation/persistence):
`varPopUp_ClassPicker`, `..._scenario`, `..._scenarioName`, `..._scenarioSplit`, `..._scenarioRole`, `..._scenarioDateTime`, `..._scenarioDate`, `..._scenarioDayOfWeek`, `..._scenarioStartTime`, `..._scenarioEndTime`, `..._scenarioStart24`, `..._scenarioEnd24`, `..._scenarioLocation`.

**Flow:** clicking the original CONTINUE button sets `varPopUp_ClassPicker = 1` to reveal the popup; the popup's close/back path sets it back to `0`.

**Why this matters (purpose):** it converts a generic desk/room booking into a *training-aware* booking tied to a specific EHRM Learning Lab / VILT session — and each prompt is personalized to the (possibly impersonated) attendee by name via `varDeskAccessControl_record.GivenName_Text` (e.g. *"Pick a SCENARIO for **Jane's** Learning Lab"*). The scenario selection also deep-links to that scenario's Workbook materials on SharePoint. See §1A Theme 4.
