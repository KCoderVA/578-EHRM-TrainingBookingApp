## Executive Summary

This release imports the substantially updated Canvas app (**v0.8.14**) into source control — the largest functional advance since the project baseline. It transforms the app from an early prototype into a role-aware application with app-wide access control, admin impersonation, zero-touch user onboarding, and a training-aware booking flow. The project-wide version jumps from `0.3.8` to `0.8.16` to align the repository release line with the Canvas app's independently-advancing `0.8.x` version series. No SharePoint schema or connector changes were made at the app-manifest level. This release also refreshes all repository documentation end-to-end.

Six distinct improvement areas are documented in full below:

1. **App-wide RBAC engine** — role resolution moved into `App.OnStart`; eight access tiers gate every screen.
2. **Impersonation** — admins can render the app as any other user for support and booking-on-behalf-of.
3. **Zero-touch onboarding** — first-launch users are auto-provisioned into `DeskAccessControl`.
4. **Training Class/Session Picker** — new `ctn_PopUp_ClassPicker` on POCSUPERVISOR ties bookings to specific Learning Lab sessions.
5. **New `alt_ManageDesks` screen** — modern responsive CRUD console for the `Desks` list.
6. **Dashboard redesign & supporting polish** — themed landing page, calendar/`chkWeekDays` refinements, assets and new component.

## Changes

### Canvas app — App-wide Role-Based Access Control (App.fx.yaml / App.OnStart)

Previously (v0.3.4) `App.OnStart` was a 1-line version stub and access gating lived in `Dashboard.OnVisible`, so it only applied once the Dashboard rendered. It has been re-architected into a full RBAC + provisioning + impersonation engine that resolves once per session and is enforced consistently across every screen. The dynamic navigation menu (`colMenu`) moved out of `Dashboard.OnVisible` into `App.OnStart`.

**How it works:** each user is classified into exactly one of eight tiers, read live from the `DeskAccessControl` list's `AccessLevel_Text` column (cached in `userAccessLevel_text`, with the boolean shortcut `user_isAdmin`). The tier drives menu contents, Dashboard messaging, calendar `DisplayMode`/`Items` filters, and admin-only controls.

| Access tier | Who / what it applies to | Effect (navigation & interaction) |
|---|---|---|
| `AccessDenied` | Blocked users | Empty menu; "ACCESS DENIED!" Dashboard notice with mailto to coordinators; calendars disabled |
| `View-only` | Read-only viewers | Home + My Bookings only (no Create New); calendars read-only |
| `User` | Standard users | Home + My Bookings + Create New; calendars editable; sees only their own reservations |
| `SuperUser` / `Manager` / `ServiceChief` / `ProjectLeader` | Elevated roles | Full menu incl. Manage Rooms; full/shared calendar |
| `AppAdmin` | Administrators | Full menu + admin-only controls (RESET, impersonation, recurrence overlays) |

### Canvas app — Impersonation ("act as another user") (Dashboard.fx.yaml)

Admins (and the developer account) see a hidden combobox + status button on the Dashboard that re-render the entire app as any selected user. Selecting a target re-resolves the target email, access record, access level, admin flag, and O365 profile, then rebuilds the menu.

**Why:** support/troubleshooting ("why can't I book?") without the user present, and booking on behalf of others (the Class/Session Picker prompts are personalized to the target). The real signed-in identity is captured separately and the auto-provisioning `Patch` only ever writes for the real user — never while impersonating.

---

### Canvas app — Zero-touch user onboarding (App.fx.yaml / App.OnStart)

If the signed-in user has no `DeskAccessControl` row, `App.OnStart` auto-`Patch`es one with a default `"User"` level, timestamps, their Entra ID, and their manager's email (via `Office365Users.Manager`), then re-reads it. Any authenticated Hines user now gets baseline access on first launch and appears in the list for a coordinator to elevate or restrict.

---

### Canvas app — Training Class/Session Picker (POCSUPERVISOR.fx.yaml)

The "Create New" flow gained the `ctn_PopUp_ClassPicker` popup (the single largest screen change, +75 KB). It walks the user through four cascading choices — **Scenario → Role → Date/Time session → Location** — captured into `varPopUp_ClassPicker_*` variables. The Scenario selection builds a deep-link into the SharePoint Learning Lab Workbook library, and selections are echoed on the Confirm screen for a final check.

### Canvas app — New `alt_ManageDesks` screen

A brand-new (~510 KB) modern responsive-layout CRUD console for the `Desks` list (add/edit/delete via `NewForm`/`Patch`/`Remove`), staged alongside the legacy `ManageDesks` ahead of a planned cutover. The app now has **22 screens** (was 21).

## Upgrade Notes / Configuration Requirements

> **Admin action required:** populate `DeskAccessControl.AccessLevel_Text` for all intended users to activate correct RBAC enforcement. Decide the default for unknown users — the app currently auto-provisions them as `User`; if `AccessDenied` is preferred, that logic must be changed in `App.OnStart`.

## Known Issues

- **Class/Session Picker not persisted:** the `varPopUp_ClassPicker_*` selections (scenario/role/session/location) are displayed on the Confirm screen but are not yet written in the SUBMIT `Patch`; they must be wired into the SharePoint record before they can drive attendance reporting.
- **App-internal version drift:** the msapp label (`v0.8.14`), `App.OnStart` `varRepoVersion` (`0.8.12`), the hardcoded Dashboard timer stamp, and the `VERSION` file (`0.8.16`) are inconsistent and should be reconciled.
- **Unknown-user default:** new users default to `User` rather than `AccessDenied` (carried forward from v0.3.8).
