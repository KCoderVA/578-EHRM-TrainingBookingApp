### 🔴 2.2 — Fix the Cancellation Confirmation Button to Soft-Delete Instead of Hard-Delete

**Screen:** `MyAppts`
**File:** `src/powerApps/.unpacked/Src/MyAppts.fx.yaml`
**Container:** `Container5` (the "Confirm Cancellation?" modal overlay, `Visible: =varConfirmCancel`)
**Control:** `btnConfirmDelete_1` — the navy-blue "CONFIRM" button

**Why this matters:** The current `OnSelect` formula uses `Remove('Desk Reservations', varReservationToCancel)`, which **permanently deletes** the record from the SharePoint list. This destroys the audit trail. The correct approach is a **soft-delete**: patch `Active_choice` to `"false"` so the record is preserved but moves from `gallUpcoming` to `gallPast`.

**Current code (exact):**
```yaml
btnConfirmDelete_1 As button:
    ...
    Fill: =RGBA(9, 33, 98, 1)
    ...
    OnSelect: |-
        =Remove('Desk Reservations',varReservationToCancel);UpdateContext({varConfirmCancel:false})
    ...
    Text: ="CONFIRM"
    Visible: =varConfirmCancel
```

**Change to make:** Replace the `OnSelect` formula and change the `Fill` color so the destructive action is visually clear (red instead of navy).

**Fixed `OnSelect` formula:**
```powerfx
=Patch(
    'Desk Reservations',
    varReservationToCancel,
    {
        Active_choice: {Value: "false"}
    }
);
Refresh('Desk Reservations');
UpdateContext({varConfirmCancel: false})
```

**Fixed `Fill` color (optional but recommended — red for destructive action):**
```yaml
Fill: =RGBA(184, 0, 0, 1)
```

**Why:** `Patch()` updates the existing SharePoint record's `Active_choice` column to `"false"` instead of deleting it. The `gallUpcoming` filter already requires `Active_choice.Value = "true"`, so the cancelled reservation immediately moves out of the upcoming list. The `gallPast` filter already includes `Active_choice.Value = "false"`, so the cancelled reservation appears there. The `Refresh('Desk Reservations')` call ensures both galleries reload without requiring a screen navigation.

**Complete updated `btnConfirmDelete_1` block (only changed properties shown):**

| Property | Current value | Fixed value |
|---|---|---|
| `Fill` | `=RGBA(9, 33, 98, 1)` | `=RGBA(184, 0, 0, 1)` |
| `OnSelect` | `=Remove('Desk Reservations',varReservationToCancel);UpdateContext({varConfirmCancel:false})` | *(full formula above)* |

### 🟢 5.5 — Complete the "Desk Reservation" → "Training Booking" Terminology Migration

**Where:** Across the Canvas app source (`src/powerApps/.unpacked/Src/*.fx.yaml`), the SharePoint list/column names, and supporting docs.
**Already acknowledged** as an expected future change in [`docs/PROJECT_STATUS.md`](../PROJECT_STATUS.md) ("The screen and list naming still reflects the original desk/room reservation terminology … Renaming/re-modeling fields and labels to fully training-centric terminology is an expected future change").

**Why this matters:** The app inherited "desk reservation" naming from its baseline template (`Desk Reservations`, `DeskAccessControl`, `Desks`, `gallUpcoming`/`gallPast`, "Manage Rooms/Desks"). For a product branded as the **EHRM Training & Booking App**, the mismatched vocabulary makes it feel adapted rather than purpose-built.

**Why this is a phased, careful change (NOT a blind find-and-replace):**
- **UI labels and variable names** are safe to rename freely (e.g., button text, screen titles, `col*`/`var*` names).
- **SharePoint list and column names are a BREAKING change.** Per the versioning policy in `.github/copilot-instructions.md`, renaming SharePoint schema that breaks existing data/automation is a **MAJOR** version bump. Renaming `Desk Reservations` → `Training Reservations` would break every `Patch`/`Filter`/`LookUp` reference in the app *and* the `AppUserList` flow, and would orphan existing list data.

**Recommended approach:**
1. **Phase 1 (safe, do first, likely a MINOR bump):** Rename only user-visible labels, screen titles, gallery captions, and internal Power Fx variable/collection names to training-centric terms. No SharePoint schema change.
2. **Phase 2 (deferred, MAJOR bump):** Plan a proper SharePoint schema migration (new lists/columns + data migration + updating every formula and the flow). Track this as its own release with a data-migration runbook under `config/runbooks/`.
3. Document the rename map (old term → new term) in the release notes so reviewers can follow the diff.

**Priority rationale:** 🟢 for Phase 1 (cosmetic polish); Phase 2 is effectively a v0.4.x+/v1.0 item — see also Section 6.

### 🟢 5.6 — Add a Booking Confirmation / Notification Flow

**Where:** New Power Automate flow under `src/powerAutomate/` (a sibling to the existing `AppUserList` flow), and/or a `Office365Outlook.SendEmailV2` call in the Canvas app booking submit logic (`chkWeekDays.fx.yaml`).
**Related to** the "Email confirmation on booking" row already listed in Section 6 (Deferred) — this item **expands and promotes** that idea with concrete guidance.

**Why this matters:** The Outlook and O365 Users connectors are **already connected** (confirmed in the connector manifest and `docs/PROJECT_STATUS.md` — "Connectors: Office 365 Outlook, Office 365 Users, SharePoint"). The data needed for a confirmation email (trainee, supervisor via `Office365Users.ManagerV2`, date/time, location) is already captured during booking. A confirmation/notification adds professional polish and closes the loop for users — especially valuable once cancellation (2.1/2.2) is live, since users will expect symmetric "you booked" / "you cancelled" messaging.

**Recommended scope (start small):**
1. **Booking confirmation email** — on successful `Patch('Desk Reservations', …)` in `chkWeekDays`, send `Office365Outlook.SendEmailV2` to the trainee (and optionally the supervisor captured on the `POCSUPERVISOR` screen) summarizing the booking.
2. **Cancellation confirmation email** — extend the soft-delete `OnSelect` from item 2.2 to notify the trainee that their reservation was cancelled (pairs naturally with the optional Outlook event deletion in item 3.3).
3. **Choose Canvas vs. Flow:** an in-app `SendEmailV2` call is fastest; a dedicated Power Automate flow triggered by the SharePoint item create/update is more robust and testable, and keeps email logic out of the UI. For long-term quality, prefer the flow, and give it its own `src/powerAutomate/<flowName>/README.md` (per the documentation rule in `copilot-instructions.md`).

**Guardrails:**
- Guard optional recipients with `If(!IsBlank(...))` (same pattern as item 3.3) so missing supervisor emails don't error.
- Do not hard-code sender addresses; use the `vah_NotificationEmailFrom` environment variable already defined in `src/solution.xml` (added in v0.3.4).
